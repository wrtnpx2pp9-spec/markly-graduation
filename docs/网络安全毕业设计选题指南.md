# 从 Markly 出发：大学网络安全毕业设计怎么选题

本文面向网络空间安全、信息安全及相关专业的本科学生，先讨论选题方法，再结合 Markly 给出可以独立完成的研究与实现方向。内容使用简体中文；题目和工作量是建议，最终以学校任务书、导师要求及个人基础为准。

公开教学仓库：[wrtnpx2pp9-spec/markly-graduation](https://github.com/wrtnpx2pp9-spec/markly-graduation)。建议以标签 `v1.0.0-education.1` 为实验基线，并为自己的改动建立独立分支。运行方式见 [README](../README.md)，业务规则见 [产品使用说明](产品使用说明.md)。本文描述的课题大多尚待学生实现，不能当作该版本已经完成的安全功能或实验结论。

## 一、先想清楚：网络安全毕设要解决什么问题

一个有说服力的网络安全毕业设计，通常需要讲清楚四件事：保护什么资产，攻击者具备什么条件，设计了什么防护，以及用什么证据证明防护有效。系统页面有多少、代码有多少行，可以体现工程量，却不能直接说明安全研究的深度。

Markly 本身是生活记录与学习监督平台。把它部署起来、增加几个管理页面，比较接近普通软件系统开发。要转成网络安全方向，应把研究对象收敛为其中的一条安全边界，例如“管理员会话撤销后，旧请求是否还能执行敏感操作”，或“服务端的外部通知请求是否只能到达批准的目的地”。平台为课题提供真实业务载体，新增安全机制、验证工具和实验分析才是学生需要完成的主体工作。

网络安全也包括 Web 应用安全、身份认证、访问控制、隐私保护和安全审计。不过，不同专业对毕业设计的要求并不相同。如果任务书明确要求网络层协议、流量检测或网络设备实验，应先与导师确认：本平台可以作为被保护业务端，但仅增加 Web 权限校验不能直接称为网络入侵检测系统。

建议用一句话描述选题：**针对某个明确场景下的安全风险，设计并实现某种机制，通过对照实验评价其保护效果和使用代价。**

例如，“学习监督系统的设计与实现”范围很大，安全问题不突出；“面向协作平台的高风险操作再认证机制设计与验证”则明确了保护对象、机制和验证方式。

## 二、如何把一个方向筛成能完成的题目

### 1. 先盘点已有基础，避免重复计算成果

Markly 已有密码 scrypt 派生、随机会话、库内令牌摘要、HttpOnly Cookie、登录限流、角色及对象权限、草稿版本校验、归档冻结和通知队列。它还包含相当数量的回归测试。这些可以作为基础和研究材料，但不能在论文中改写成学生独立新增的功能。

已有防护也不意味着没有课题空间。例如，存在会话令牌不等于有完整的空闲超时和会话自助管理；角色检查不等于所有关系、历史批次和异步状态都已经得到系统化验证。选题的第一份成果，应是一张“已有实现—待研究问题—本人新增工作”对照表。

### 2. 选一个主要问题，再配一到两个支撑模块

本科阶段更适合完成一条可验证的主线。例如，以高风险操作再认证为主，配合会话管理和安全审计；以 Webhook 安全外联为主，配合目的地策略和本地验证工具。不要把多因素认证、WAF、区块链、深度学习、蜜罐和零信任同时放进一个题目。

可以参考 [OWASP ASVS](https://asvs.owasp.org/) 梳理安全需求，但应明确实际选择和验证的条目。采用标准作为需求参考，不等于完成标准全量验收，也不等于取得安全认证。

### 3. 在开题前确定实验能否做出来

一个可落地的课题，应有合法正常请求，也有边界、失败或受控异常请求；应能重复建立测试数据，记录防护前后结果。可以先用少量场景做可行性验证，再决定是否立题。

如果原版在某一场景已经正确拒绝，就如实记录已有防护，不必为了论文故意制造“原版存在漏洞”的结论。测试工具类课题可以通过独立实验分支中的受控故障注入评价检测能力；这类故障必须标为人工变体，不能算成原项目真实漏洞。

### 4. 选择能解释的指标

优先考虑正常功能成功率、危险样本阻断率、误拒率、撤销生效时延、敏感数据残留数量及处理耗时。每个指标都要说明样本、分母和测试环境。只展示扫描器分数，或没有对照地宣称“安全性提升 90%”，难以支撑结论。

可按下面五个问题各评 1—5 分，比较候选方向。评分用于个人决策，不是学校评分标准：业务边界是否清楚；代码能否修改；实验能否本地重复；结果能否量化；时间和依赖是否可控。任何一项明显不可行，都应先缩小范围。

## 三、结合本项目可以做的八个方向

以下难度是对熟悉基本 JavaScript、HTTP 和数据库操作的学生的相对估计，不是难度认证。通常只选择一个方向，不要求全部实现。

| 方向 | 可采用的题目 | 本人新增工作的重点 | 难度与适合情况 |
| --- | --- | --- | --- |
| 账号与会话安全 | 面向协作平台的管理员会话管理与高风险操作再认证机制设计与验证 | 空闲失效、会话撤销、绑定会话与用途的再认证、并发状态验证 | 中；适合第一次做安全工程课题 |
| 访问控制验证 | 面向多角色协作平台的关系与状态感知授权测试方法设计与实现 | 权限矩阵、测试生成、状态迁移与故障注入评价 | 中；适合后端、软件测试方向 |
| 服务端安全外联 | 基于目的地约束的 Webhook 出站请求安全控制设计与实现 | 目的地策略、DNS 与连接绑定、重定向控制、验证工具 | 中偏高；希望突出网络边界控制时可选 |
| 浏览器隐私保护 | 多账号 Web 应用的浏览器草稿与离线缓存隐私保护研究 | 草稿保留期、共享设备清理、跨标签保护、静态缓存白名单 | 中；适合前端和数据隐私方向 |
| 智能体安全 | 面向业务智能体的工具调用权限与数据最小化机制研究 | 按用途授权、工具参数校验、敏感字段限制、撤权与通知审批 | 高；适合有后端基础且愿意设计实验集的学生 |
| 安全审计 | 面向协作平台的安全事件审计与日志完整性校验机制设计 | 事件模型、执行结果、敏感读取审计、完整性校验与检索 | 中；适合安全运营和后端方向 |
| 文件处理安全 | 面向 DOCX 计划导入的安全解析与资源预算控制研究 | 解析资源预算、失败清理、边界样本和资源消耗评价 | 中；适合文件安全、程序分析方向 |
| 通知安全 | 基于签名与投递标识的业务通知认证及重放防护机制设计 | 接收方验签、时间窗口、固定投递键、重放与恢复实验 | 中；适合协议应用与消息系统方向 |

如果尚无明确偏好，建议先看会话安全；如果喜欢接口测试和业务分析，选择授权测试；如果希望网络控制特征更突出，选择安全外联；如果主要掌握前端，选择浏览器隐私。智能体方向虽然有研究空间，但实验变量较多，不宜只因名称热门就选。

## 四、五个可以进一步写成开题报告的方案

### 方案一：管理员会话与高风险操作再认证

**建议题目：面向协作平台的管理员会话管理与高风险操作再认证机制设计与验证。**

研究问题是：在管理员会话有效期间，如何进一步限制密码重置、权限变更和通道配置等敏感动作，并保证会话撤销、账号停用或角色变化后，旧请求不能继续使用原来的授权。

当前代码已有随机会话、摘要存储、密码重置撤销会话等基础；默认会话期限为 30 天。运营 AI 有局部二级验证，但不代表所有管理员敏感动作均具备统一的近期再认证。因此，课题应研究补充机制，而不是重新包装现有登录功能。

建议把实现范围控制为：会话空闲失效、本人会话列表与撤销、三个选定敏感接口的近期再认证。再认证凭证应绑定原会话、用途和必要的目标对象，设置有效期，按业务决定是否一次性消费；异步动作执行前重新校验状态。多因素认证可以列为拓展，不必在最小版本中同时完成。

实验可准备 20—30 个固定场景，涵盖正常操作、过期、空闲、跨会话、跨用途、替换目标、撤销后重放及并发撤销。只在本人创建的本地虚构会话上模拟这些行为。分别统计正常操作成功率、非法重放拒绝率和撤销生效时延，并比较保护前后的请求耗时与操作步骤。

代码入口：`src/security.js`、`src/repo/session.repo.js`、`src/controllers/auth.ctrl.js`、`src/controllers/admin.ctrl.js`。已有边界测试可从 `test/auth-session-boundaries.test.js` 阅读。设计原则可参考 [OWASP 会话管理指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

这一题的答辩重点，是如何绑定和撤销授权，以及如何处理并发；不是单独展示一个登录页面。

### 方案二：关系与状态感知的授权测试

**建议题目：面向多角色协作平台的关系与状态感知授权测试方法设计与实现。**

Markly 不仅有管理员、监督者和被监督者三种角色，还存在当前合作、历史合作、多监督者、私有草稿、已归档目标等状态。课题可以研究：如何把这些业务规则转成可审阅、可执行的权限矩阵，并自动发现接口实现与规则的偏差。

建议先选计划详情、每日提案、执行提交、复盘确认和历史读取五类操作。用 JSON 或 YAML 描述“主体—资源—动作—关系—状态—版本—预期结果”，生成固定测试数据和请求，输出失败位置与证据。预期规则需要根据产品说明独立审阅，不能直接把被测函数的返回值当作正确答案。矩阵驱动的基本思路可参考 [OWASP 授权测试自动化指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Testing_Automation_Cheat_Sheet.html)。

例如，同一执行人同时与两位监督者合作时，一位监督者不能仅因服务同一个人而取得另一位的计划详情；但原合作双方可能仍有历史只读权限。因此，“关系结束”不能一律等同于“所有历史读取都拒绝”。测试应区分读取与写入、当前批次与旧批次。

建议建立 60—120 个有明确预期的组合用例，再在独立实验分支中加入少量受控故障，例如遗漏归属条件、忽略终态或未检查版本，评价工具能否发现它们。每个故障变体应单独记录，不能把相同缺陷的几十次请求计成几十个漏洞。

评价可以包括矩阵组合覆盖率、人工确认的误报、可达故障变体检出率和执行耗时。检出率只说明对指定变体集的效果，不等于发现所有权限问题。代码入口是 `src/router.js`、`src/scope.js`、相关控制器及 `test/`。本题的主要交付物是策略描述、验证工具、样本集和分析报告。

### 方案三：Webhook 安全外联与 SSRF 防护

**建议题目：基于目的地约束的 Webhook 出站请求安全控制设计与实现。**

这一题关注服务器向外发起网络请求的边界。当前 Webhook 配置入口需要管理员权限，已有 HTTP(S) 协议检查、URL 用户信息限制和超时；目的地、DNS 结果及重定向仍有可研究的控制空间。应将其表述为高权限外联安全改进，不应写成已经发现匿名 SSRF 漏洞。

建议实现一个共享外联策略模块：明确允许的域名和端口，对解析结果分类，拒绝不符合策略的目的地址，默认不跟随重定向，并限制超时和响应资源。关键是把批准的解析结果与实际连接绑定，不能先检查一次 IP，再让普通请求库重新解析域名。HTTPS 连接仍应校验证书和主机名，不能为了固定连接地址而关闭 TLS 验证。设计可参考 [OWASP SSRF 防护指南](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。

实验全部使用本地模拟端点、注入 DNS 解析器和受控传输层，覆盖允许地址、拒绝地址、IPv4/IPv6、多条解析结果、DNS 变化、重定向、超时和超量响应。模拟允许目标时，可以由测试传输层转到本地服务；不要为方便测试而放宽正式策略，也不需要访问真实云元数据或任何第三方内网。

建议准备 30—40 个边界用例，记录是否发起连接、实际连接目标、返回结果和资源消耗。危险样本必须验证请求未到达禁止端点，不能只看接口返回了错误码。评价正常目标成功率、危险目标阻断率、误拒率和额外请求耗时。

代码入口：`src/controllers/setting.ctrl.js`、`src/notify.js`、`test/webhook-cleanup.test.js`。最小范围只覆盖 Webhook；其他模型或辅助服务的出网策略可作为后续扩展，避免一次改造全部通道。

### 方案四：多账号草稿和离线缓存的隐私保护

**建议题目：多账号 Web 应用的浏览器草稿与离线缓存隐私保护研究。**

这一题保护共享设备中的私人数据。当前草稿已有按账号分键的隔离，Service Worker 也排除了 API 请求；可以继续研究保留期限、主动清理、跨标签同步和明确的静态缓存范围。账号分键只能约束正常页面的读取逻辑，不能当作本机加密。

建议实现一个草稿管理层，统一记录账号、类型、保存时间、过期时间和清理代际；为共享设备提供明确的保留选择和清理入口。清理后，迟到请求不能重新写回旧内容。缓存层只允许批准的公开静态资源，业务响应不因路径变化而自动进入离线缓存。

用真实启用 Service Worker 的浏览器完成双账号、多标签、退出、失效、断网、慢响应和过期组合实验；分别检查 localStorage、sessionStorage 和 Cache Storage。关闭 Service Worker 的浏览器回归不能作为缓存安全的证明。存储接口的行为可参阅 [MDN CacheStorage 文档](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage)。

评价正常草稿恢复率、清理后敏感残留条目数、错误账号恢复次数，以及清理与恢复耗时。需要同时检验用户体验：不能通过一退出就无提示丢弃全部输入来宣称“隐私问题解决”。本题也不应宣称能防御设备管理员、恶意浏览器扩展或所有同源 XSS。

代码入口：`public/js/core.js`、`daily-planning.js`、`goal-workspace.js`、`plan-import.js`、`life.js` 和 `public/sw.js`。在隐私规则已经明确的情况下，这一方向比较适合偏前端的学生。

### 方案五：业务智能体的工具权限与数据最小化

**建议题目：面向业务智能体的工具调用权限与数据最小化机制研究。**

Markly 的计划 AI 与运营 AI 提供了研究载体，但两者权限不同：计划编排主要产生待核对草稿，运营工具能读取部分业务记录，并可在显式授权下发送通知。课题应选定其中一种智能体，不要把模型本身是否听话与服务端工具是否正确授权混为一谈。

可以设计任务级授权描述，固定允许的数据类别、用户范围、工具、有效期和通知对象；在每次工具执行时校验，输出只包含必要字段。模型输入材料视为不可信数据，敏感正文不能仅凭工具名称或提示词就获得读取资格。工具权限和参数校验必须在模型外执行，相关原则见 [OWASP 提示词注入防护指南](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)。

首先使用假模型固定地产生越范围调用、错误对象、撤权后调用和未批准通知，验证确定性的授权边界。若需要评价提示词注入，再在另一个实验阶段选择明确版本的真实模型，记录提示、配置、重试预算、样本划分和正常任务表现；费用和数据范围要先确定。固定工具调用测试通过，只能证明服务端策略在这些用例中有效，不能算成真实模型的抗注入成功率。

可以评价越权工具调用阻断率、未授权字段进入模型上下文的数量、正常任务完成率、误拒率及处理开销。通知成功必须检查实际入队和接收范围，不能只看模型回复“没有发送”。代码入口：`src/plan-agent/`、`src/platform-agent/service.js`、`src/platform-agent/tool-registry.js`。

这一题变量较多，适合有余力的学生。若周期紧张，可以只做工具层授权与数据最小化，不训练模型，也不宣称实现了通用提示词注入检测算法。

## 五、其余三个方向应怎样控制范围

**安全审计方向**可以先覆盖登录失败、权限变更、敏感读取和通知发送四类事件。新增事件结构、执行结果与关联标识，再研究完整性校验。若采用哈希链，需要说明：攻击者能改写整条链且没有外部可信锚点时，单机哈希链不能证明日志绝对未篡改。检测实验可在虚构日志副本中做删除、重排和修改，评价检出率与开销，不必直接引入区块链。

**DOCX 导入方向**应承认原版已经有文件大小、正文解压量、条目数及 XML 声明检查。新增工作可以集中在总解析耗时、资源预算、失败清理和异步撤权边界，用有严格上限的小样本评价内存峰值、处理时间和正常导入成功率。无需启动 Office，也不应使用会让设备失控的大型压缩炸弹。

**通知认证与重放防护方向**可以实现本地接收器，按原始消息、时间戳和固定投递标识验签、去重，再验证密钥轮换和快照恢复。签名解决来源与内容校验，投递标识解决重复业务处理，作用不同。需要明确至少一次投递的前提，不能因一次测试未重复就宣称真实通道“恰好一次”。

这三题都可以有足够的实现和实验内容，但仍应坚持一个主问题，先把最小闭环做完整。

## 六、实验怎样设计，论文才有证据

### 固定基线，分开实现与测量

先保存基线标签、提交、依赖锁文件、运行环境和配置，再保存自己的实现提交。正常样本、边界样本与异常样本需要编号并说明预期；调参样本和最终评价样本尽量分开。如果用同一批样本反复完善规则，应如实披露，不把结果包装成对未知输入的泛化能力。

原版与改进版应在相同数据和请求序列下比较。对于原版已经通过的场景，改进后应继续正常；对于新增的控制目标，需要说明原版行为、设计要求和改进结果。所有研究数据均使用本地虚构数据、内存或临时目录，不使用真实账号、真实业务库和未授权网络目标。

### 明确指标的分母

| 指标 | 建议定义 | 解释边界 |
| --- | --- | --- |
| 正常请求成功率 | 正确完成的合法请求数 / 合法请求总数 | 同时核对预期副作用，不只看 HTTP 200 |
| 危险样本阻断率 | 在禁止副作用发生前被阻断的危险样本数 / 危险样本总数 | 只适用于所选样本与威胁模型 |
| 误拒率 | 被错误拒绝的合法请求数 / 合法请求总数 | 与阻断率同时报告，避免全部拒绝的假效果 |
| 故障变体检出率 | 被测试发现的可达故障变体数 / 注入的可达故障变体总数 | 明确变体、可达性及等价变体处理规则 |
| 敏感残留量 | 指定清理或权限撤销动作后仍可读取的敏感条目数 | 写明检查的存储位置、账号和等待窗口 |
| 性能开销 | 相同负载下改进前后的时延、吞吐、CPU 或内存差异 | 记录硬件、负载、预热、样本量和重复次数 |

性能实验可按能力选择中位数和 P95，说明计算方法；不要只取一次最快结果。出现零失败时也应报告样本数量；有限样本中的零失败不等于风险为零。上述表格没有给出达标数值，阈值应在实验前根据业务和导师要求确定。

### 保存完整的证据链

每个关键场景至少保留：样本编号、预期规则、执行命令、实际结果、数据或副作用断言、对应代码提交和局限说明。截图用于说明界面和流程，程序断言用于证明授权、持久化和网络副作用。扫描器报告可以辅助分析，但人工复核与可重复验证不可省略。

教学基线已有的测试数量和发布记录见 [验证记录](验证记录.md)。它们说明基础项目在相应环境的通过范围，不是学生新课题已经完成的实验结果。新增机制仍需自己的对照实验与回归。

## 七、一个可调整的十二周安排

下面是工作顺序示例，周数应按学校安排和个人基础调整，不是对完成时间的保证。

| 阶段 | 建议时间 | 应形成的成果 |
| --- | --- | --- |
| 理解基线与筛题 | 第 1—2 周 | 运行平台、代码阅读、已有/新增工作对照、与导师确认题目 |
| 需求与威胁建模 | 第 3 周 | 资产、攻击者前提、信任边界、范围与预期规则 |
| 最小可行验证 | 第 4 周 | 少量样本与一个机制原型，确认技术路线可行 |
| 主要设计与实现 | 第 5—7 周 | 完整机制、必要界面、异常处理和定向回归 |
| 对照与边界实验 | 第 8—9 周 | 固定样本集、性能与安全指标、失败结果分析 |
| 集成与完善 | 第 10 周 | 业务回归、部署复现说明、结果复核 |
| 论文与答辩准备 | 第 11—12 周 | 图表、论文、演示脚本、可重现源码与测试说明 |

前期没有验证通过的路线，不宜把主要实现押到最后两周。如果发现题目范围过大，优先减少保护的接口和场景，而不是删除实验分析。

## 八、开题报告和答辩可以怎样组织

开题报告可按“业务背景与问题—相关方法—已有基础—具体研究目标—技术路线—实验与指标—进度和风险”展开。相关方法应比较适用条件与不足，不必堆砌与实现无关的术语；文献引用按学校格式整理，不能编造论文、作者或实验数据。

正文可以采用以下结构：绪论；相关技术与研究现状；需求和威胁模型；方案设计；关键实现；实验与结果分析；结论与局限。章节名称可按学校模板调整。

答辩演示选择一条普通用户能理解的链路。例如，再认证题目可以依次展示正常操作、过期凭证被拒绝、撤销后迟到请求失败，以及正常业务仍可完成；外联题目可以展示批准目标可达、受控危险目标没有收到请求、正常投递功能保留。演示前准备好虚构数据和失败恢复方案。

回答“你的工作是什么”时，可以明确说：平台基础来自哪个版本，自己新增了什么策略、模块、验证工具与样本，哪些结果通过实验得到，哪些能力尚未验证。独立的工程设计、实现和可靠实验可以构成本科工作；是否满足创新性与工作量要求，仍由导师及学校评价，不需要把已有功能说成原创算法。

## 九、如何作最终选择

如果希望范围稳妥、实现和演示都比较直观，优先考虑**管理员会话管理与高风险操作再认证**。如果喜欢把复杂规则形式化并编写自动化工具，选择**关系与状态感知的授权测试**。如果更关注服务器网络出口，且愿意处理 DNS、地址与连接细节，选择**Webhook 安全外联**。偏前端的学生可选择**草稿与离线缓存隐私保护**；智能体方向则应留出更多实验与结果解释时间。

开始前，先给导师看一页简要方案：题目、一个主要安全问题、本人新增模块、三类实验和预期交付物。题目确定后再扩展功能，比先改完整个平台、最后寻找安全论点更容易控制范围。

以上建议是结合本项目结构形成的选题设计，不是所有高校通用的审核标准。技术原理和验证方法应继续查阅官方资料；具体题目名称、周期、论文格式及原创性要求以本校规定为准。
