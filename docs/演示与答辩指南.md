# 演示与答辩指南

对应版本：`1.0.0-education.1`。本指南用于准备可重复的本机演示，核心流程不依赖真实模型、微信或 Webhook。

## 1 准备演示环境

```sh
npm ci
npm run demo:seed
npm run demo
```

浏览器访问 <http://127.0.0.1:8787>，在本机编辑器读取 `demo-data/accounts.md` 的随机密码。三类演示账号为 `admin_demo`、`mentor_demo`、`student_demo`。不要把密码放到演示幻灯片、录屏、公开截图或论文附件中。

演示库固定为 `demo-data/app.db`，与普通实例的 `data/app.db` 分开。初始化脚本拒绝覆盖已存在的演示目录；保存现有成果前不要删除目录。演示服务只监听回环地址，不读取 `.env`，外部通道保持关闭。

若要展示首次初始化和注册审核，应另用空白实例流程：`npm run setup:env`、`npm start`，用本机 `.env` 中的 `SETUP_TOKEN` 创建管理员。不要同时让两个实例占用相同端口。

## 2 建议演示顺序

| 顺序 | 操作 | 需要解释的设计 |
| --- | --- | --- |
| 1 | 管理员查看用户及监督者合作授权 | 开通账号、认证和服务授权是不同状态，人数额度会在新增服务时检查 |
| 2 | 被监督者发起协商，监督者确认接手 | 接手表示进入制定计划，还不代表执行人已接受完整约定 |
| 3 | 监督者新建目标、阶段方向和日期，预览发送 | 长期目标与阶段分开，默认滚动安排不会自动铺满每日任务 |
| 4 | 被监督者先退回，再接受调整后的计划 | 退回保留旧记录，首份整套计划必须整体确认 |
| 5 | 一方提出今天的每日事项，由另一方确认 | 提案不直接改约定，不能自行确认自己的安排 |
| 6 | 被监督者勾选事项并提交，监督者要求补充后通过 | 提交与完成不同，以监督者确认作为完成口径 |
| 7 | 展示阶段复盘和双方确认规则 | 只完成近期几天不等于滚动阶段到期，确认要绑定正文版本 |
| 8 | 追加下一阶段，再归档目标或结束合作并查看历史 | 续期、归档和解绑各自独立；历史保留真实状态 |

阶段复盘受日期与状态规则限制。不要为了现场演示修改机器时钟、绕过 API 授权或直接改数据库。可提前在隔离演示中准备已具备条件的记录；不能完成的时间条件，用对应自动化回归说明，并注明这是测试证据而非刚刚完成的现场操作。

## 3 双角色操作安排

推荐使用两个浏览器配置文件或两个独立浏览器分别登录监督者和被监督者。普通同一浏览器的多个标签页共享 Cookie，切换账号会影响另一标签页；这可以用于说明账号切换保护，但不适合作为同时登录两角色的方法。

管理员使用第三个独立会话，仅在需要授权或查看管理结果时进入。演示记录只填写虚构昵称、学习目标和任务，不录入同学的手机号、认证材料或生活隐私。

## 4 失败场景也应展示

选择两三项准备好操作和预期结果：

- 用无关用户访问另一个合作对象的计划，服务端拒绝读取。
- 从旧页面确认已变更的安排或复盘，返回版本冲突并要求重新核对。
- 尝试提前提交未来日期的打卡，返回明确失败反馈。
- 保存期间切页或重新打开表单，迟到响应不应覆盖新输入。
- 归档后尝试继续修改执行记录，原有历史仍可读取，但修改被拒绝。

失败演示必须在自己的本机隔离数据中完成，不对公共站点或其他人的实例执行测试。

## 5 建议保留的证据

| 证据 | 内容 |
| --- | --- |
| 版本 | 仓库地址、版本标签、本人修改的提交和开发环境 |
| 需求与权限 | 三角色用例、对象可见范围、主要状态和异常反馈 |
| 数据模型 | 从实际表结构核对的 ER 图、关系与索引说明 |
| 业务操作 | 双角色协商、接受、每日提案、提交审核及历史截图 |
| 回归 | 修前失败、修后通过、具体测试命令和断言 |
| 集成验证 | 完整 `npm run release:check` 的固定报告及起止摘要 |
| 限制 | 未验证的真机、真实通道、生产配置、安全或容量条件 |

截图、日志和测试报告保存在本机 `output/`，不应直接上传包含凭据或个人信息的原始产物。公开说明只保留脱敏后的必要结果。

## 6 可讨论的问题

- 为什么使用单实例 SQLite？它简化了部署和事务，但多实例共享文件、写并发和容量有边界；不要用未经测量的吞吐数字作保证。
- 为什么接受计划需要事务？关系、合作批次、容量和整套计划必须共同生效或共同回滚。
- 为什么有内容版本和记录快照？前者保证确认的是已读内容，后者保存确认时的历史统计。
- 为什么通知先写 outbox？把业务提交与网络发送分开，支持重试；至少一次投递仍需接收方防重，不能声称真实通道恰好一次。
- 为什么请求结束后仍需等待后台工作？HTTP 断开不表示密码计算、导入或模型回调已经结束，数据库关闭需要等待在途处理。
- 当前还有哪些不足？可结合 [学习与二次开发指南](学习与二次开发指南.md) 选择会话、缓存、外联或隐私边界，给出明确改进和验收，而不是泛称“已全面安全”。
