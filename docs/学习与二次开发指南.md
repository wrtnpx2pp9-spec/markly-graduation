# 学习与二次开发指南

对应版本：`1.0.0-education.1`。建议先按 [README](../README.md) 运行独立演示模式，再阅读代码。核心操作不需要外部模型、微信或 Webhook。

## 1 阅读路线

1. 阅读 [产品使用说明](产品使用说明.md)，列出管理员、监督者和被监督者各自的动作，分清合作、目标、阶段、执行日和任务。
2. 从 `server.js` 进入 `src/app.js` 和 `src/router.js`，确认请求如何读取、鉴权、匹配和返回。
3. 选择“创建计划 → 接受计划 → 每日安排 → 执行审核”一条路径，依次阅读控制器、仓储和对应测试。
4. 阅读 `src/db.js` 与初始化中的其他模块，查看表结构、索引和兼容迁移，不对演示库直接执行破坏性 SQL。
5. 从 `public/js/boot.js`、`core.js` 和各业务模块观察 API 调用、渲染、表单、加载状态及账号切换保护。
6. 最后阅读通知、outbox、调度器和可选 AI 模块，理解同步事务如何与异步工作衔接。

建议用浏览器开发者工具观察一次真实请求，再到代码定位；不要仅凭文件名推断某个动作的完整权限和副作用。

## 2 分层和职责

| 位置 | 主要职责 | 阅读时关注 |
| --- | --- | --- |
| `server.js` | HTTP、静态资源、超时、启动和停止 | 请求体大小、异常、连接关闭与异步处理结束的区别 |
| `src/app.js` | 依赖装配与控制器注册 | 共享数据库、服务实例、测试注入边界 |
| `src/router.js` | 路由、认证与角色门禁 | 公开路由和受保护路由、Cookie 写请求限制 |
| `src/controllers/` | 参数校验、业务授权、流程和事务协调 | 同一动作最终如何决定对象归属、状态和版本 |
| `src/repo/` | 查询和持久化 | 参数绑定、稳定排序、分页、作用域和索引 |
| `src/db.js` | 基础表结构、迁移与连接生命周期 | 迁移幂等、旧行保留、SQLite 的单实例约束 |
| `public/js/` | 前端流程与状态反馈 | 输入保留、重复提交、迟到响应和会话失效 |
| `test/`、`scripts/ui-*.cjs` | 回归与真实浏览器流程 | 测试准备、实际断言和未验证边界 |

这不是所有模块都完全一致的分层范本：部分控制器和服务仍直接使用 SQL。二次开发时应围绕修改的业务逐步收敛，避免只为形式统一而改写全库。

## 3 核心数据模型

| 数据表或表组 | 业务含义 | 关键边界 |
| --- | --- | --- |
| `users`、`sessions` | 账号、角色和登录会话 | 密码派生值与令牌不能作为普通资料返回 |
| `registration_applications` | 注册申请与审核结果 | 申请通过不自动等于监督者取得服务授权 |
| `user_profiles`、`certifications`、`certification_reviews` | 公开资料、认证材料和审核 | 公开摘要与私有核验材料分开 |
| `supervision_relations`、`supervision_periods` | 当前合作关系和历史批次 | 同一双方重新合作应有新批次 |
| `service_requests`、`request_messages` | 目标协商及留言 | 确认接手与接受正式计划分开 |
| `plans` | 长期目标和阶段 | `phase` 为目标，`cycle` 为阶段；`planning_mode` 区分滚动和兼容固定日程 |
| `plan_days`、`plan_day_items`、`plan_day_comments` | 执行日、当天事项、留言与反馈 | 提交、确认和休息分别有自己的状态 |
| `daily_plan_proposals` | 双方协商的每日安排提案 | 草稿私有，按版本确认后应用 |
| `phase_stage_reviews` | 双方复盘、确认与锁定快照 | 确认绑定实际阅读的内容版本 |
| `tasks` | 普通任务 | 个人任务与共享监督任务的动作权限不同 |
| `life_logs` | 个人生活记录 | 与合作执行记录分开授权 |
| `notifications`、`notification_outbox` | 站内消息与外部待投递事件 | 业务和入队原子保存，外部请求在事务之后执行 |
| `audit_logs`、`activity_events` | 审计与业务活动 | 记录用途不同，不能代替业务状态 |
| `settings`、AI 和微信相关表 | 可选能力的配置及任务 | 默认不接入真实外部服务，机密按单独规则保管 |

有些业务表由相应模块初始化或迁移创建，不全部集中在 `src/db.js` 的第一段建表代码中。绘制数据库图前，应结合实际初始化代码和临时数据库的表结构核对。

## 4 三个值得重点说明的设计

### 接受计划是一个业务事务

首份协商计划被接受时，要同时核对账号、监督者服务授权、容量、协商状态、合作批次和整套计划，再建立关系并激活安排。任一步失败都不应留下“关系已建但计划未生效”的半成品。可结合 `test/plan-agreement-boundary.test.js`、`test/plan-lifecycle.test.js` 和合作相关测试阅读。

### 双方确认绑定所读版本

每日安排和阶段复盘不是简单地保存两个布尔值。用户必须针对阅读过的内容确认；正文变化后需要清除旧确认，旧页面的版本不能确认新内容。确认本身不能不断改变正文版本，否则双方可能永远无法对齐。可阅读 `test/stage-review-version.test.js`、`test/draft-conflict.test.js`。

### 异步结果不能覆盖新状态

网络、模型、密码校验和导入解析完成前，账号可能停用、会话可能撤销、合作可能结束、草稿可能已发送。最终写入前要重新核验当前授权和对象状态。停止服务也需要等待在途任务回调完成，再关闭数据库。可阅读 `test/auth-session-boundaries.test.js`、`test/plan-agent-draft-boundaries.test.js`、`test/server-request-drain.test.js`。

## 5 权限分析方法

为每个接口画一行表格：请求方身份、对象归属、当前合作批次、允许状态、请求版本、成功副作用和失败反馈。不要用“已经登录”代替对象权限。

至少准备以下测试用户：管理员、当前合作双方、第三名无关用户、另一个监督者、已停用用户。再组合未登录、旧会话、结束合作、归档和旧版本场景。列表、详情、统计、分页和消息跳转都要验证同一可见范围。

管理员的管理能力不能直接等同于普通合作方的能力；对管理员敏感读取或外部模型处理的进一步限制，可以作为明确的二次开发课题。

## 6 测试与证据

```sh
npm test
npm run release:check
```

先运行与修改相关的测试；业务与浏览器流程集成后，再冻结应用、测试和部署输入运行完整门槛。报告的起止摘要不同，不能把中途变动代码的一次运行视为发布通过。

有价值的回归应该先在旧行为下失败，再验证修复。测试数据只使用内存或系统临时目录，不把账号、数据库、截图和日志提交到公开仓库。真实微信、供应商模型、生产 HTTPS 和灾难恢复必须另有证据；模拟发送成功不能代替真实实收。

## 7 可选二次开发选题

选择其中一项，写清需求、范围、设计、实现和结果，避免一次重做整个系统。

| 选题 | 可交付内容 | 验收示例 |
| --- | --- | --- |
| 管理员会话管理 | 空闲失效、会话列表、撤销和敏感操作再认证 | 撤销后旧会话失败，迟到请求不能恢复权限 |
| 浏览器草稿管理 | 保留期、共享设备模式、当前账号清理入口 | 不串号、不误删其他账号、过期内容不恢复 |
| 外部通知安全适配 | 目的地限制、签名、重放防护与受控适配器 | 内网跳转拒绝，同投递键不重复产生业务结果 |
| CSP 与前端输出加固 | 减少内联事件、严格脚本策略、属性归一 | 恶意标签作为文字显示，核心表单仍可完成 |
| 运营数据最小化 | 字段白名单、按用途授权、报告脱敏 | 未授权正文不进入模型上下文，权限撤销后停止工具调用 |
| 可观测性与恢复 | 队列积压指标、备份失败提示、隔离恢复演练 | 指标可解释，恢复后历史一致且外部副作用受控 |

这些是待开发方向，不代表当前版本已经实现。新增费用、真实外部通道、角色与共享范围变动应先明确需求，再实施。

## 8 学习成果的表达

说明原有功能与新增工作的边界。引用本仓库版本、提交和依赖来源；保留开源许可证。论文或设计说明中可用自己的运行截图、测试数据、接口追踪和失败复现支撑结论，避免把已有代码或自动生成内容写成未经验证的原创成果。
